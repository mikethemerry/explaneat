# Verifying Experiment 2 (thesis Ch 7, reproducibility across seeds)

This is a checklist for proving every final Experiment 2 number to yourself. For each number it
says where the number comes from, which command recomputes it, and what that command does to
the database. The commands are read-only on the database. Every one was run on 2026-11-18,
and the last section records what each one gave.

## What Experiment 2 is

There are three studies. Each has 10 seeds (0–9) and runs for 100 generations.

| Study | Experiment names | Runs CSV | Explanation CSV (v4) |
|---|---|---|---|
| Adult | `10seed-adult-s<seed>` | `runs.csv` (rows `adult`) | `explanations_v4.csv` (rows `adult`) |
| Heart-100 | `10seed-heart100-s<seed>` | `runs_heart100.csv` | `explanations_heart100_v4.csv` |
| Churn | `churn100-s<seed>` | `../churn/runs_churn100.csv` | `../churn/explanations_churn100_v4.csv` |

- **Explanations:** the frozen v4 run (`V4_RUN.md`, tag `methodology-v4-freeze-2026-11-11`).
- **Prompts:** `PROMPTS_V4.md`.
- **Records:** `explanations_v4/<label>.json`.
- **Plain-language layers:** `plain_language_v4/<label>.json`.
- **Labels:** `adult-s3`, `heart100-s0`, `churn100-s7` and so on.

**Use `exp2_summary.md`, not `summary.md`, for the explanation numbers.** `summary.md` (from
`make_figures.py`) still reports the old v3 explanations. Its run-level rows (performance,
size, shape, training time) are the same runs, and they agree with `exp2_summary.md` cell for
cell. `verify_exp2.py stats` checks this.

**Deleted genomes (Heart-100, churn100).** The intermediate-generation genomes of these runs
were deleted on 2026-11-10, with your approval.
- **Why that was safe:** the replay had first been verified bit-identical with
  `verify_prefix_reproduction.py` on 2026-11-06. Heart against Heart-100 matched

## 1. Training runs reproduce bit for bit (replay)

```bash
PYTHONHASHSEED=0 uv run python experiments/10seed/replay_verify.py heart100 0   # ~1.5 min
PYTHONHASHSEED=0 uv run python experiments/10seed/replay_verify.py churn100 0   # ~10-14 min
PYTHONHASHSEED=0 uv run python experiments/10seed/replay_verify.py adult 0      # ~1.5-2 h
uv run python experiments/10seed/replay_verify.py --summary                     # table -> replay_verify/SUMMARY.md
```

To examine one genome, replay part of a run with `--generations N` and pass
`--dump GEN:KEY --log-info --tag=-a`. This saves the replayed genome and prints the backprop
log lines, which compare directly with `logs/<run>.log`. The adult-s0 and adult-s5 diagnoses
were made this way. adult-s0's result predates the tie-count check, so its "Tie counts" cell in
`SUMMARY.md` is "-". Adult keeps every genome, so `verify_exp2.py runs` recounts its ties from
the DB, and they match.

**What it does.** It re-runs the seed in memory, exactly as `run_seed.py` did:
- the same config, seed and split;
- the scaler fitted in memory and asserted equal to the stored one;
- `PYTHONHASHSEED=0`, float64 and one torch thread.

It runs the code at the run's **recorded commit**, imported from a detached worktree,
`.claude/worktrees/replay-<commit[:7]>`. To create one:

```bash
git worktree add --detach .claude/worktrees/replay-4126fe2 4126fe2508c64707c305172bf76d3cf3aa7f4617
```

The commits are 4126fe2 and cc48129 for Adult, 4126fe2 for Heart-100, and 901fad4 and ad20d2d
for churn100. The script refuses to run if the worktree is at another commit, or if the Python,
torch or numpy version differs from the run's `hardware_info`.

The population's DB writes are replaced by in-memory capture. The connection is also opened
with `default_transaction_read_only=on`, so a write would fail.

**What it checks:**
- **Every generation:** the `populations` row (size, species count, and best, mean and stdev
  fitness, compared exactly).
- **Every genome the DB still holds for the run:** the NEAT key, the fitness (exact) and the
  md5 of the serialised genome. That md5 is `md5(genome_data::text)` in the DB against the md5
  Postgres computes for the replayed genome.
- **The selected genome:** best training fitness, ties to the earliest generation and then the
  lowest key, compared with the runs CSV.
- **The tie counts** of the runs CSV.

**Results:** `replay_verify/<label>.json`, with the table in `replay_verify/SUMMARY.md`.

**Is HEAD's training path the same?** Not always, so the replay uses the recorded commits.
- **At HEAD:** `backproppop.py`, `neuralneat.py`, `db/population.py` and `uv.lock` all differ
  from the recorded commits. The changes are the `mask_phantom` option, ancestry tracking, the
  fail-loud evaluation and the lock file. There is also an uncommitted edit to
  `core/neuralneat.py` in the working tree.
- **Between the recorded commits:** the training path is identical. `4126fe2` = `cc48129`
  and `901fad4` = `ad20d2d` file for file. `4126fe2` → `901fad4` adds two unused constants to
  `neuralneat.py`.
- **Library versions:** torch 2.2.2, numpy 1.26.4 and neat-python 0.92 are the same in the
  lock files and in the repository venv. The replay runs on that venv.

## 2. Run-level numbers (performance, size, shape, training time)

```bash
uv run python experiments/10seed/verify_exp2.py runs     # ~5 min; explaneat_dev, read-only
```

This runs `compute_runs.py --skip-paper` and `../churn/compute_churn_runs.py --prefix
churn100`, both with `--out-dir` pointing at a temp folder. Both scripts open READ ONLY
transactions, and `verify_exp2.py` also sets the read-only connection option. It then compares
every column of the 30 rows with the stored CSVs.

| Number | Column (runs CSV) | How it is computed |
|---|---|---|
| Selected genome | `genome_id`, `genome_key`, `generation_of_best` | Highest stored training fitness; ties go to the earliest generation, then the lowest NEAT key |
| Train AUC (and check against stored fitness) | `train_auc`, `stored_fitness`, `fitness_match_1e-6` | NeuralNeat forward pass on the split's training rows, z-scored with the stored scaler, float64 |
| Test AUC and 95% CI | `test_auc`, `test_auc_ci_lo`, `test_auc_ci_hi` | Percentile CI from 10,000 paired bootstrap resamples, `RandomState(42)` |
| Test accuracy | `test_acc_0.5` | p > 0.5 |
| Size and shape | `inputs_connected`, `hidden_nodes`, `phenotype_connections_enabled`, `genome_genes_total`, `depth`, `skip_connections`, `direct_io_edges`, fan-in, structural proxy | Phenotype graph; definitions in the `compute_runs.py` docstring |
| Training time | `wall_clock_hours` | `end_time - start_time`. Adult's *net* time subtracts the pause and throttle intervals in `RUN_INCIDENTS.md` (`make_figures.py`) |

The per-study medians, IQRs and ranges of these columns are in `exp2_summary.md`
(`verify_exp2.py stats`, below).

## 3. Explanation numbers (coverage, function preservation, recheck, timing)

```bash
uv run python experiments/10seed/verify_exp2.py explanations   # ~15 min; explaneat_v4, read-only
```

For each of the 30 records, this re-runs three things against `explaneat_v4` (read-only
connection) and compares the results with the stored record:
- `check_explanation.py`: function preservation, the leaf closed-form and numeric errors,
  operation counts and the hierarchy. It runs in a fresh process per genome, because the last
  bits of the closed-form error depend on what the process evaluated before (section 7);
- `get_coverage`: structural and compositional coverage;
- the end-of-protocol recheck (`xn.py --recheck`, recheck v3, claims off, the record passed in).

| Number | Source field | Command for one genome |
|---|---|---|
| Structural and compositional coverage | record `verified_by_orchestrator.structural_coverage` / `compositional_coverage`; CSV `structural_coverage`, `compositional_coverage_tool` | `uv run python experiments/10seed/xn.py get_coverage '{"genome_id": "<id>"}'` |
| Hierarchy complete, full coverage | `verified_by_orchestrator.hierarchy.complete`, `full_coverage` | `check_explanation.py <id>` (`hierarchy`). Full coverage = both coverages 1.0, hierarchy complete, and function preserved < 1e-9 |
| Function preservation (max abs Δ output, train) | `function_preservation_max_abs_err` | `uv run python experiments/10seed/check_explanation.py <id>` |
| Closed-form (displayed) and numeric leaf errors | `closed_form_max_abs_err`, `numeric_max_abs_err` | same |
| Leaves, compositions, splits, identity nodes, consolidations | `n_leaf`, `n_composition`, `op_counts` | same (`op_counts`); leaves and compositions come from the record |
| Recheck: mismatches, needs_review, complete_ok | `verified_by_orchestrator.recheck_summary`, `complete_ok` | `uv run python experiments/10seed/xn.py --recheck <id> --record experiments/10seed/explanations_v4/<label>.json` |
| Explanation time (Claude) | record `start` / `end` → CSV `claude_minutes` | `build_explanations_csv.py` |
| Within the 3 h box | record `within_budget` | from the record |

Run all of these with the read-only URL:
`DATABASE_URL='postgresql://localhost/explaneat_v4?options=-c%20default_transaction_read_only%3Don'`.
- `xn.py --recheck` is read-only on the database. It writes nothing unless you give it a
  summary path as its second argument. With claims off it touches no cache either.
- `check_explanation.py` and `get_coverage` only read.
- `xn.py <tool>` (for example `get_coverage`) only reads the database, but it appends one line
  to `logs/mcp_calls.jsonl`. That file is untracked and is what the explanation timing used
  during the run; the timing reported comes from the record `start` / `end`.
- **Do not run `verify_record.py`.** It rewrites `explanations_v4/<label>.json`.

**The needs_review count can only fall on a re-run.** The stored records have 6 (Adult),
1 (Heart-100) and 2 (Churn) needs_review items. All are the `amend_evidence` provenance flag
described in `V4_RUN.md`. After the run, `fix_amended_provenance.py` repaired the provenance
lists behind them in `explaneat_v4`, so a fresh recheck finds fewer. `verify_exp2.py` accepts a
lower count and flags any other difference.

## 4. The per-study tables and the CSVs

```bash
uv run python experiments/10seed/verify_exp2.py csvs    # seconds, no DB
uv run python experiments/10seed/verify_exp2.py stats   # seconds, no DB -> exp2_summary.md
uv run python experiments/references/rashomon.py && git diff --stat experiments/references/results   # seconds, no DB
```

- **`csvs`:** rebuilds the three v4 explanation CSVs from the records into a temp folder
  (`build_explanations_csv.py --dir explanations_v4 --suffix _v4 --out-dir`) and compares them
  byte for byte.
- **`stats`:** writes `exp2_summary.md`. It has four parts:
  - the explained counts: full coverage within the box, complete_ok, mismatches, needs_review,
    unchecked free-text sentences, draft text objects and median explaining minutes;
  - the per-study median [IQR] (min–max) table for every metric `make_figures.py` reports;
  - a per-seed table (test AUC with CI, size, leaves, function preservation, complete_ok,
    minutes);
  - the near-equivalence counts.

  It also checks its 48 run-level cells against `summary.md`.
- **Near-equivalence (ε-Rashomon membership in AUC terms):** the number of seeds whose test AUC
  is at least the reference minus ε, for ε ∈ {0.005, 0.01, 0.02}. There are three references:
  the best seed, logistic regression and gradient boosting. The method is in
  `experiments/references/results/rashomon.md` and the counts in `experiments/references/results/rashomon_counts.csv`.
  `rashomon.py` rebuilds them from the runs CSVs and `experiments/references/results/baselines.json`, and the
  `git diff` must be empty.
  - **References:** `experiments/references/baselines.py` refits them on the same split (minutes of
    CPU, no DB).
  - **Population-level shares:** `experiments/references/rashomon_population.py` reads the
    final-generation genomes from `explaneat_dev`, which are kept for all three studies.

Two numbers in `V4_RUN.md` are rounded differently from `exp2_summary.md`:
- **The median explaining minutes** in `V4_RUN.md` are 21.6 for Adult and 18.2 for Churn.
  They come from the unrounded record times, 21.55 and 18.16. The CSV-based median rounds each
  genome first and gives 21.5 and 18.1.
- **"Draft sentences"** in `V4_RUN.md` (1487, 1180, 1353) is the count of every text object in
  the stored draft. `exp2_summary.md` reproduces it as "draft text objects". The review tool's
  `draft_sentences()` leaves out the summary and gives lower counts.

**Numbers that did not reproduce exactly:**
- **Adult replay: 2 genomes of 250,000 differ, one in adult-s0 and one in adult-s5.**

  | Run | Generation | NEAT key | Stored fitness | Replayed fitness | Δ |
  |---|---|---|---|---|---|
  | adult-s0 | 38 | 9533 | 0.8952257749512352 | 0.8952258181877769 | 4.3e-8 |
  | adult-s5 | 39 | 9861 | 0.8949883072537961 | 0.894988177544171 | 1.3e-7 |

  `replay_verify/adult-s0-diagnosis.json` and `adult-s5-diagnosis.json` hold the details,
  including every differing gene.
  - **The replay is deterministic.** adult-s0 was replayed again to generation 39, twice and
    independently (`adult-s0-partial39-{a,b}.json`). Both gave the same fitness and md5 as
    the full replay. adult-s5's partial replay to generation 40 equals its full replay too.
  - **Only trained values differ.** The structure is identical: same node and connection
    genes, enabled flags, activations, aggregations and responses. Only biases and weights
    differ:

    | Run | Biases differing | Weights differing | Largest difference | Median difference |
    |---|---|---|---|---|
    | adult-s0 | 14 of 22 | 88 of 165 | 8.6e-6 | 2.7e-7 (biases), 8.1e-8 (weights) |
    | adult-s5 | 15 of 20 | 87 of 158 | 1.9e-5 | 8.8e-7 (biases), 7.3e-7 (weights) |

    That pattern is what a small change inside the genome's 5-epoch backprop produces.
  - **The original run computed it that way.** With `--log-info`, the replay prints the same
    backprop log lines as the original run (mean improvement, best improvement, best loss per
    generation). Against `logs/adult-s<seed>.log`, only one value differs in each run, and it
    is the mean improvement of the affected generation:
    - adult-s0, generation 38: -0.15442984606935325 originally, -0.15442987679482822 in the
      replay (116 of 117 values identical);
    - adult-s5, generation 39: -0.08260515951343508 originally, -0.08260516398005815 in the
      replay (119 of 120 values identical).

    The best improvement and best loss are identical. So the stored rows are exactly what
    the runs computed and logged at the time; they were not changed afterwards.
  - **The rows were not modified after the run.**
    - `created_at` = `updated_at` on both rows, and on every row of both runs.
    - The database has no triggers, and nothing references either row (no parent links,
      explanations or training metrics).
    - Adult rows carry no parent links, and these keys exist only in their own generation.
  - **No pause overlaps.** adult-s0 generation 38 ran 13:36–13:40 and adult-s5 generation 39
    ran 13:48–13:52 NZDT on 2026-11-03. The first SIGSTOP was at 14:13:54. Neither log has a
    warning or error.
  - **No effect downstream.** Every later generation reproduces exactly. A child inheriting
    one of the differing genes would have differed, so neither genome passed on a differing
    gene. All 10 selected genomes are identical.
  - **Most likely cause:** in the original processes, the backprop arithmetic of one genome
    came out differently, at the level of floating-point rounding, once per run in two of the
    ten runs. At the time 30 runs were going at once on 14 cores. How the original processes
    computed differently is not established. Possibilities include CPU-kernel paths that
    depend on memory alignment, and hardware or OS effects. The replay can't tell them apart
    because it does not reproduce the event. It is not a database change, a pause, a code
    difference (every run used its recorded commit) or a logged error.
  - **What this means for the bit-identity claim:** README §4 says a seeded run "should
    reproduce every genome and fitness exactly". On these three studies 255,054 of 255,056
    stored genomes and all 3,000 population rows reproduce, along with all 30 selected
    genomes. The claim holds except for these two genomes, and both are documented above.
- **Closed-form error, last bits:** `closed_form_max_abs_err`, the displayed closed form's max
  error, depends in its last bits on what the same Python process evaluated before.
  - **Example:** for adult-s2, `check_explanation.py` on its own gives 0.058889693843529045,
    as stored. Run after two other genomes in one process, it gives 0.0588896938435397.
  - **Where it showed:** four Adult genomes differed by about 1e-14 in the first batch run.
  - **Fix:** `verify_exp2.py` now runs `check_explanation.py` in a fresh process per genome,
    as the stored values were made, and then all 30 match exactly.
  - **Effect:** none on any reported number. They are shown to 3 decimals.
- **Two numbers in `V4_RUN.md` are rounded differently** from the CSV-based tables:
  - the median explaining minutes, 21.6 and 18.2, against 21.5 and 18.1 (see section 4);
